## Operational rules

A player qualifies for Master if they have prior individual Master participation, an individual Rookie championship, or an individual Light championship. Team participation, team championships, non-winning Light participation, Champions participation, and ranking points do not grant individual Master eligibility. New Team tournaments lock to Master while historical Light Team records remain intact.

Eligibility queries check completed Events by Player ID, individual Entry and EntryParticipant, and champion Result. Because historically migrated tournaments can lack `record_applied_at`, that timestamp is not required for eligibility. Name matching succeeds only when an exact existing Player name is unique; players sharing a name are blocked for admin review.

## Lifecycle from announcement to records

1. New regular individual announcements default to combined Rookie and Master intake. Existing separate flows for Light and Champions stay unchanged.
2. `league_intakes` links one announcement to two standard Master and Rookie Events that share a `competition_edition_id` and round number. Both internal Events are created with the announcement, while operators pick the division at bracket creation. No separate database or Match/Result store is added. Edition storage follows [Competition editions](COMPETITION_EDITIONS.md).
3. Applicants see a single registration form. Existing INSERT grants and RLS stay in place, and a `BEFORE INSERT` trigger checks history to pick the target Event. Direct inserts into the other Event follow the same rule, and duplicate registration across both divisions is blocked. One exception applies: a player who won the same edition's Rookie division and had records finalized can register separately for the open Master division while keeping their Rookie registration and party. General registration does not create new Player rows.
4. The admin response table and CSV export show both divisions together along with per-division headcounts.
5. During bracket creation, operators pick the announcement, choose Master or Rookie, and select Single or Double Elimination independently for each division. For walk-ins who did not apply, operators use `'참가자 추가'`; an admin RPC finds or creates the Player and inserts a manual Registration on that Event. Eligibility checks match normal intake and run again at participant confirmation. Players cannot be added after a bracket is created.
6. The shared party submission button on the announcement looks up the applicant's name to find the Event owning their Registration and submits there. Completing one division does not block submissions for the other. Submissions, Snapshots, and `final_submission_id` are never copied across Events.
7. Each Event uses its existing runtime, Result, RankingAward, and official party freeze/release flows. Rookie awards no points and Master follows the existing payout policy. Applying or reverting records on one division does not affect the other.
8. Announcement deletion checks downstream facts on both sides, then runs the final check, cancels both Events, and removes the announcement in a single DB transaction. If a new registration arrives right before deletion, both the announcement and Events stay intact. Other fields in shared data are preserved on the server.

## Existing announcements

Creating or editing an announcement does not set a bracket format. New Events start with `competition_format = NULL`, and the creation RPC saves the chosen format alongside the runtime. Even if an older announcement stored a format, operators can choose again on first bracket creation, and editing an announcement preserves the format of any existing bracket. Champions Qualifiers and Finals also pick Single or Double independently, and Qualifiers track elimination at 1 loss (Single) or 2 losses (Double). Apply in order: `docs/db/bracket_manual_registration.sql`, `docs/db/bracket_format_at_creation.sql`, then the matching frontend.

Promoting a same-edition Rookie champion does not move their Registration. The server verifies the completed Rookie champion Result and Player ID, then creates a new Master Registration. Existing Submissions, Snapshots, and `final_submission_id` are not copied, so the player submits a fresh Master party. `is_completed_rookie_champion` reads only public facts, and only admins can execute `add_bracket_manual_registration`.

Existing single-league announcements are never converted automatically. An operator can convert an open individual Master announcement only when it matches an existing announcement ID cleanly and has no downstream Submissions, Entries, brackets, or Results. Conversion keeps the existing Master Event ID, `season_id`, and `round_number` and adds only the Rookie Event. If registrations already exist, the same transaction assigns each one to its eligible Event while keeping registration IDs, responses, and timestamps. Any name collision, invalid player link, duplicate name, or non-standard registration aborts the entire conversion.

The server blocks conversion once submission or participation data exists. In particular, there is no automatic migration that moves a Registration after submission or clones an official party to another Event.
